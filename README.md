# CoreML Video Upscaler

Core ML の超解像モデル（Real-ESRGAN）で動画を 1 フレームずつ拡大し、フル HD などの
指定解像度で書き出す macOS アプリ／CLI です。音声トラックは再エンコードせずそのまま
引き継ぎます。

- **UpscaleKit** — 変換の中身（Core ML 推論・タイル分割・動画の読み書き）
- **upscale** — バッチ処理向け CLI
- **VideoUpscaler.app** — ドラッグ＆ドロップで使う SwiftUI アプリ
- **tools/convert_realesrgan.py** — Real-ESRGAN の公開重みを `.mlpackage` に変換

外部の Swift パッケージには依存していません。

## 必要なもの

- macOS 14 以降（開発・動作確認は macOS 27 / Apple M4 Pro）
- Xcode 16 以降（Swift 6 ツールチェイン）
- Python 3.10 以降（モデル変換時のみ）
- `--fps`（フレームレート変換）を使うなら macOS 15.4 以降と対応 GPU

## 1. モデルを用意する

Core ML モデルは同梱していません。次のスクリプトで Real-ESRGAN の公開重みを
ダウンロードして変換します。

```bash
cd tools
python3 -m venv .venv
./.venv/bin/pip install -r requirements.txt
./.venv/bin/python convert_realesrgan.py --model animevideo-x4v3 --tile 256
```

`Models/realesrgan-animevideo-x4v3-t256.mlpackage` ができます。変換の最後に
PyTorch の出力と Core ML の出力を突き合わせて、ずれが FP16 の丸め範囲かを確認します
（想定は PSNR 55 dB 以上）。

### 選べるモデル

`--model` で切り替えます（`--list` で一覧）。

| 名前 | 倍率 | 規模 | 向いている素材 |
| --- | --- | --- | --- |
| `general-x4v3` | x4 | 1.2M | 汎用。動画の既定 |
| `animevideo-x4v3` | x4 | 0.6M | アニメ動画。最速 |
| `x4plus` | x4 | 16.7M | 実写。高画質だが重い |
| `x4plus-anime` | x4 | 4.5M | イラスト・アニメ。高画質 |
| `x2plus` | x2 | 16.7M | 実写。720p 素材向け |

`--tile` はモデルが一度に処理する正方形の一辺です。大きいほどタイル枚数が減って
効率は上がりますが、1 回の推論のメモリと時間が増えます。既定の 256 から始めるのが
無難です。

## 2. CLI から使う

```bash
swift build -c release --product upscale
.build/release/upscale 入力.mp4
```

出力先を省略すると入力と同じ場所に `入力.upscaled-1080p.mov` を作ります。

### 書き出し解像度の決まり方

既定は **「縦 1080・横は元の縦横比のまま」** です。16:9 でない素材でも黒帯は入りません。

| 指定 | 864x480 の素材でどうなるか |
| --- | --- |
| `--short-side 1080` | **1944x1080** — 短辺を 1080 に。縦動画なら横が 1080 になる |
| 省略（既定） | **1944x1080** — 縦を 1080 に合わせ、横は比率どおり |
| `--height 1440` | 2592x1440 |
| `--width 1920` | 1920x1066 — 横を 1920 に合わせ、縦は比率どおり |
| `--width 1920 --height 1080` | 1920x1066 — その枠に収まる最大サイズ（`--fit contain`） |
| `--width 1920 --height 1080 --fit fit` | 1920x1080 — 枠に固定し、上下に黒帯 |

幅・高さは映像コーデックの都合で偶数に丸めます。

### 縦動画も混ざるとき

`--height` は縦を基準にするので、縦長の素材だと逆に小さくなります（480x854 → 606x1080）。
向きが混ざる素材は `--short-side` を使うと、どちらでも同じ基準で揃います。

| 素材 | `--short-side 1080` の結果 |
| --- | --- |
| 横 864x480 | 1944x1080 |
| 縦 480x854 | **1080x1922** |
| 回転メタデータ付き（データ 854x480 + 90 度） | データ 1922x1080・**表示は 1080x1922** |

回転はメタデータとして引き継ぐので、プレイヤー上の見た目で短辺が揃います。
アプリの解像度プリセットも短辺基準です。

```bash
.build/release/upscale 入力.mp4 出力.mov \
  --model Models/realesrgan-animevideo-x4v3-t512.mlpackage \
  --height 1080 --codec hevc --device cpuAndNeuralEngine
```

主なオプション（全ては `--help`）:

| オプション | 既定 | 内容 |
| --- | --- | --- |
| `--short-side` | — | 短辺をこの長さに。`--width` / `--height` より優先。縦横が混ざる素材向き |
| `--height` | 1080 | 出力の高さ。省略すると幅と元の縦横比から決まる |
| `--width` | 元の比率から自動 | 出力の幅。両方指定すると `--fit` の枠になる |
| `--fit` | `contain` | 幅と高さを両方指定したときの合わせ方。`contain`（比率を保って枠に収める・余白なし）/ `fit`（枠に固定して余白を黒）/ `fill`（はみ出しを切る）/ `stretch` |
| `--codec` | `hevc` | `hevc` / `h264` / `proRes422` |
| `--bitrate` | 自動 | Mbps。既定は解像度 × フレームレートから算出 |
| `--fps` | 元のまま | 出力フレームレート。VideoToolbox のフレーム補間 (VTFrameRateConversion) を GPU 上で使ってフレームを生成してから超解像にかける（macOS 15.4 以降が必要） |
| `--device` | `all` | `all` / `cpuAndGPU` / `cpuAndNeuralEngine` / `cpuOnly` |

| `--overlap` | タイルの 1/8 | タイルの重なり幅（入力ピクセル） |
| `--passes` | 1 | モデルを重ねて適用する回数。2x モデル + `--passes 2` で 4 倍まで拡大してから縮小（スーパーサンプリング。高画質・約 5 倍遅い） |
| `--no-audio` | — | 音声を引き継がない |
| `-f`, `--force` | — | 出力先が既にあれば上書き |
| `--inspect` | — | 変換せず、演算の実行先の内訳を表示 |
| `--benchmark` | — | 変換せず、推論だけの素のスループットを測定 |

### フレームレートも変える

```bash
.build/release/upscale input.mp4 out60.mov --fps 60
```

`--fps` を指定すると、超解像の前に VideoToolbox の `VTFrameRateConversion`
（ML ベースのフレーム補間）で目標フレームレートへ変換します。中間ファイルは作らず、
「フレーム補間 → タイル分割して超解像 → エンコード」を 1 パスで流します。

- **macOS 15.4 以降が必要**です（`VTFrameRateConversionConfiguration` の対応 OS）。
  それより前の macOS で `--fps` を指定するとエラーで終了します。
- フレーム補間は **GPU**、超解像は **Neural Engine** と、別の実行資源を使います。
  重ねて動かす最適化はしていませんが、フレーム補間は数十 fps 出るのに対し超解像は
  1〜数 fps 程度なので、全体の速度はほぼ超解像側で決まります。
- 目標が元のフレームレートより高いときだけ補間します（24→60 など）。元より低いとき
  （ダウンコンバート）は、間引いて直前のフレームをそのまま使います。
- 出力フレーム数は `元動画の尺 × --fps` を四捨五入した値です。音声は無変換のまま
  そのフレーム数ぶんの尺に合わせて引き継がれます。

## 3. アプリとして使う

```bash
./scripts/make_app.sh
open build/VideoUpscaler.app
```

`Models/` にある `.mlpackage` はビルド時に `.mlmodelc` へコンパイルされてバンドルに
入るので、アプリ側のモデル一覧にそのまま出てきます。動画をウィンドウにドロップして
「アップスケール開始」を押すだけです。処理中はキャンセルできます。

「フレームレート」のプルダウンで 元のまま / 30 / 60 を選べます（CLI の `--fps` と同じ
VTFrameRateConversion を使うので macOS 15.4 以降が必要）。

## コミュニティモデルを使う

`--weights` にローカルの `.pth` を渡すと、SRVGG Compact 構造（AnimeJaNai / AniSD など
OpenModelDB のアニメ向けモデルの多く）を形状から自動判別して変換できます。

```bash
./.venv/bin/python convert_realesrgan.py --weights weights/2x_AnimeJaNai_HD_V3_Compact.pth --tile 512
```

2 倍モデルで 480p → 1080p（2.25 倍）を作る場合は 2 通りあります。

- そのまま実行 — 2 倍拡大した後、残り 12.5% を vImage で引き伸ばす。速い
- `--passes 2` — 4 倍まで拡大してから 1080p へ縮小（スーパーサンプリング）。
  線の輪郭が明確に締まるが、2 パス目は 1 パス目の 4 倍の画素を処理するため約 5 倍遅い

コミュニティモデルのライセンスは多くが CC-BY-NC 系（非商用限定）です。配布元を確認してください。

## 仕組み

Core ML の画像入力は解像度が固定なので、フレームをそのまま流し込めません。

1. `AVAssetReader` でフレームを 32BGRA の `CVPixelBuffer` として取り出す
2. モデルの入力解像度（例 256x256）のタイルに分割して推論する
3. 拡大後のキャンバスへ貼り合わせる
4. 目標解像度へ vImage でリサイズする
5. `AVAssetWriter` で書き出す。音声は `outputSettings: nil` で無変換コピー

タイルはラスタ順に処理し、各タイルは左辺・上辺だけを既存ピクセルへ線形フェードで
混ぜます。右辺・下辺は後続タイルがフェードインしてくるので、こちらでフェードアウト
させる必要はありません。フレーム端でタイルがはみ出す分は、黒ではなく端のピクセルを
複製して埋めます（黒だと拡大時に縁へ滲みます）。

Core ML モデルは image 入出力（`ct.ImageType`）で変換してあるため、Swift 側は
`CVPixelBuffer` をそのまま渡せます。0-1 正規化と 0-255 への戻しはモデル内部に
埋め込まれています。

## Neural Engine で動いているか確かめる

速度を比べるだけでは「本当に Neural Engine に載ったか」は分かりません。
`--inspect` は `MLComputePlan` を使って、演算ごとの割り当てを実行前に読み出します。

```bash
.build/release/upscale --inspect --device cpuAndNeuralEngine
```

```
演算の割り当て (全 43 個):
  Neural Engine     40 個 (93.0%)
  CPU                2 個 (4.7%)

Neural Engine 以外に回る演算 (推定コスト合計 0.32%):
  ios17.mul        CPU            コスト 0.202%
  ios17.cast       CPU            コスト 0.115%
```

CPU に残る 2 つは、出力を 0-255 に戻すスケーリングとその型変換です。**推定コストの
合計は 0.32%** なので、畳み込みを含む計算の実質すべてが Neural Engine で動いています。

### どこまで Neural Engine を使い切れているか

`--benchmark` は動画パイプラインを通さず、推論だけを繰り返して素のスループットを測ります。
並行度を変えられるので、実行先が飽和しているかが分かります。

```bash
.build/release/upscale --benchmark --device cpuAndNeuralEngine
```

```
  並行度   1秒あたり   1推論あたり   逐次比
       1     24.58 回       40.7 ms   x1.00
       2     27.15 回       36.8 ms   x1.10
       3     27.17 回       36.8 ms   x1.11
       4     27.18 回       36.8 ms   x1.11
```

並行度 2 で頭打ち＝**Neural Engine の上限は 27.2 回/秒**（このモデル・タイル 512 の場合）。
逐次に投げると 1 回あたり 4ms ぶん遊ぶので、パイプラインは推論を先読みして重ねています。

変換の実行結果には、実際に出た推論スループットが表示されます。

```
  解像度      : 864x480 -> 1944x1080
  フレーム数  : 1489 (1 フレーム 2 タイル)
  所要時間    : 109.7 秒 (13.58 fps)
  推論        : 2978 回 (27.2 回/秒)
```

27.2 回/秒 は上の `--benchmark` が出した上限と同じ値です。つまりこの素材では
**Neural Engine を空き時間なく回しきれています**。

### 推論を重ねる仕組み

Neural Engine は 1 回の推論を待つ間に次の入力を受け取れるため、逐次に投げると遊びが出ます。
パイプラインは 3 段階で推論を重ねています。

1. **タイルの先読み** — 1 枚先のタイルの推論を走らせながら、手前のタイルを貼り合わせる
2. **フレームをまたぐ先読み** — 手前のフレームの結果を待つ前に、次のフレームの推論を始める
3. **書き出しの並行化** — リサイズとエンコードを、次のフレームの推論と並行に流す

これで逐次実装の 10.9 fps から 13.6 fps まで上がりました（62 秒の素材で 137 秒 → 110 秒）。
貼り合わせの順序は変えていないので、出力は逐次実装とビット単位で一致します
（同じ素材の同じフレームを突き合わせて PSNR = inf を確認済み）。

### 実行先の選び方

`--device` の実測（M4 Pro / animevideo-x4v3 / 864x480 → 1080p / 3 秒クリップを 3 回ずつ）:

| 指定 | fps | 備考 |
| --- | --- | --- |
| `cpuAndNeuralEngine` | 10.3 / 10.4 / 10.3 | Neural Engine に固定。ばらつきが小さい |
| `all` | 10.4 / 6.3 / 4.2 | Core ML 任せ。実行によって落ち込むことがある |
| `cpuAndGPU` | 8.4 | |
| `cpuOnly` | 4.0 | |

`all` は Core ML が実行先を選ぶため GPU に振られることがあり、実測では回によって
速度が安定しませんでした。Neural Engine を確実に使いたい場合は
`--device cpuAndNeuralEngine` を明示してください。

### タイルサイズと速度

| タイル | 1 フレームあたり | fps |
| --- | --- | --- |
| 256 | 8 タイル | 10.3 |
| 512 | 2 タイル | 10.8 |

総演算量は同じですが、タイルが大きいほど推論の呼び出し回数が減り、わずかに有利です。
864x480 の素材なら 512 が扱いやすいサイズです。

## 制限

- **SDR (BT.709) 前提**です。HDR 素材を通すと色が変わります。
- タイル分割を使う場合、モデルの倍率は整数である必要があります（フレーム全体が
  1 タイルに収まる場合のみ非整数でも動きます）。
- 音声は無変換コピーなので、出力コンテナがそのコーデックを受け付けない場合は
  音声トラックが落ちます。
- 入力トラックの全サンプルを書き出します。edit list で冒頭が一部隠されている素材では、
  再生開始位置が数十ミリ秒ずれることがあります。
- `--fps` によるフレーム補間には macOS 15.4 以降と対応 GPU が必要です。それより前の
  環境では利用できません（[フレームレートも変える](#フレームレートも変える) 参照）。
